Natural Hazard Monitoring at global scale

I led the setup and maturation of BeZero Carbon's Natural Hazards product line — geospatial risk-assessment pipelines for drought, wildfire, tropical cyclone, and sea-level rise that powered ratings analysts, product teams, and client-facing dashboards.

Problem

Carbon project ratings need defensible hazard exposure scores.

Carbon projects — REDD+, ARR, IFM and others — sit on the land for decades. A wildfire, drought, cyclone, or rising sea level can erase a project's carbon storage overnight, but most rating methodologies treated hazard exposure as an afterthought.

BeZero needed quantitative, repeatable, and auditable hazard exposure pipelines for every project polygon globally — feeding both internal ratings analysts and external client dashboards.

Approach

One pipeline pattern, four hazard heads.

I designed a shared geospatial pipeline pattern — ingest → clip-to-project → model → score → export to Snowflake — with hazard-specific feature engineering and severity logic at the modelling step.

Drought

  • Long-horizon SPI / SPEI indices from reanalysis
  • Trend + anomaly decomposition for chronic vs acute stress
  • Severity scored against historical baselines per biome

Wildfire

  • Active-fire and burn-scar histories at project polygon
  • Fire-weather feature stack (FWI components)
  • Recurrence × severity scoring with seasonality

Tropical cyclone

  • Best-track wind swaths joined to project geometry
  • SAR-based inundation overlays where available
  • Frequency × peak-intensity exposure curves

Sea-level rise

  • Coastal / low-lying project flagging from DEMs
  • Projected inundation under multiple SSP scenarios
  • Time-to-impact reporting per project tier
Engineering

Reproducible by default; provenance tracked end-to-end.

  • Built ingestion on STAC / COG conventions so every input had a discoverable, versioned source.
  • Scheduled batch workflows in Prefect with retry, alerting, and idempotent writes to Snowflake / PostGIS.
  • Reusable xarray / dask pipelines kept memory bounded for global runs on modest compute.
  • Outputs versioned per project polygon — analyst could trace any rating back to inputs, model version, and run date.
  • Standardised QA layer so a regression in any hazard head surfaced before reaching client dashboards.
Outcome

From research code to a product line analysts depend on.

  • Set up and matured a new Natural Hazards product line from scratch.
  • Powered ratings analysts, product teams, and client-facing dashboards with interactive charts and automated summaries.
  • Established the pattern that subsequent hazard heads were built against — onboarding new ones became a feature-engineering exercise, not a pipeline rebuild.
  • Produced internal documentation and supported stakeholder calls with clear technical explanations.
